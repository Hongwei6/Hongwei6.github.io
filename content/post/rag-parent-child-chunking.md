传统的分块方式存在一个矛盾：小分片语义粒度细，便于精确匹配，但缺乏上下文；大分片包含丰富上下文，但可能降低检索相关性。

父子分片通过**将大块文本作为父块保留上下文，将其切分为多个子块用于检索**，兼顾两者优势。

## 父子分片的必要性

### Embedding 模型 token 限制

Embedding 模型有 token 数限制。例如 `text-embedding-v4` 模型，单批次最大 token 数为 8192。如果分片长度超过限制，无法进行 embedding，也就无法存入向量库。

![Embedding 模型 token 限制](/hero/rag-parent-child/embedding-token-limit.png)

因此，任何分片方式都需要支持 `chunkSize` 参数，避免超过模型限制。

### 切分后语义丢失

按照 token 限制切分后，完整内容可能被拆分到不同分片，导致语义不完整。

之前使用 overlap 做冗余重叠，但对文本有效，对表格和图片则无法解决。例如：

```markdown
![这是一段图片描述](这是一个图片的地址)
```

如果这段内容被切分开，就会破坏完整性。

## 基本思路

### 文档分片阶段

以 Markdown 标题分片为例：一个标题下的内容放在一起，但超过 `chunkSize` 后需要拆分。

例如 `我是一个完整的句子` 按 `chunkSize=5` 拆分，得到：
- `我是一个完`
- `整的句子`

实际得到三个分片：
- **父分片**：`我是一个完整的句子`
- **子分片1**：`我是一个完`
- **子分片2**：`整的句子`

子分片使用 embedding 模型做向量化，保存到向量数据库。父分片因为太长无法直接嵌入，用关系型数据库存储完整内容，不做语义相似度检索。

存储结构：
```
父分片：id=5 → MySQL
子分片1：parentChunkId=5 → pgvector
子分片2：parentChunkId=5 → pgvector
```

子分片的 metadata 中记录 `parentChunkId`，标识其对应的父分片。

### 文档检索阶段

1. 只有子分片做了索引构建，保存在向量数据库
2. 语义相似度召回时，只通过子分片召回
3. 召回后判断是否为子分片，如果是则取出父分片 ID
4. 从关系型数据库查询完整父分片，替换子分片内容
5. 将父分片交给 LLM 生成回答

## 总结

父子分片的核心优势：
- **检索阶段**：使用子分片，语义粒度细，提高匹配精度
- **生成阶段**：使用父分片，上下文完整，保证回答质量

避免单纯使用大块导致的"高召回但低精度"，或单纯使用小块导致的"高精度但低召回/低生成质量"。

需要注意的问题：
- 父分片去重
- 查询加速
- 内容替换逻辑

目前 LangChain、Spring AI、LangChain4j 中都没有直接实现父子分片，需要自行实现。
