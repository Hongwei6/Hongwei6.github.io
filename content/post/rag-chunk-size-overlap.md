RAG 里 `chunk_size` 和 `overlap` 怎么定？我的结论是：从通用推荐值出发，按文档类型和语言调整，最后用实验收敛——和调线程池核心线程数是一个套路。

## 先明确单位和通用起点

注意单位是**字符**，不是 token。从 token 角度换算更直观：一个 token 约等于 1.5–2 个汉字或 3–4 个英文字符。

- 起点：512 或 1024 token。部分 embedding 模型有 512 token 上限（如 bge-small-zh），阿里百炼的 text-embedding-v3/v4 是 8192
- 纯中文文档：chunkSize 500–1000 字符
- 英文文档：2000–3000 字符
- overlap：chunkSize 的 10%–20%

两个边界别踩：

| 参数 | 风险 |
| --- | --- |
| chunkSize < 300 字符 | 语义碎片化，丢上下文（父子分片能缓解，但可能引入上下文过长的新问题） |
| chunkSize > 1024 字符 | 无关信息稀释核心语义，检索精度下降，LLM 上下文负担和成本上升 |
| overlap = 0 | 切分边界处信息丢失，相邻块语义断裂 |

## 按文档类型差异化

不同文档对上下文的依赖不同：

| 文档类型 | chunkSize（字符） | overlap（字符） | 考量 |
| --- | --- | --- | --- |
| 纯文本/文章 | 256–512 | 32–64 | 保持段落连贯 |
| 技术文档/代码 | 384–512 | 64 | 函数、类、代码块不能被截断 |
| 法律/合同 | 320–512 | 48–64 | 保住条款和推理链，中文法律条文 320 往往更好 |
| FAQ/知识库 | 300–600 | 30–60 | 每块聚焦一个问答对 |
| 长文本/论文 | 512–1024 | 100–200 | 论证和证据链需要更大上下文 |

## 我项目里的定量做法

先按 markdown 标题分段（段落、特殊符号也行），数一下全文分成多少段。假设 2000 段。

然后定义最差情况：一个分段被 chunkSize 二次拆开后可能无法召回。如果要求召回率 95%，就意味着能接受 100 个分段二次拆分失败。

接下来调 chunkSize，统计有多少 chunk 的 metadata 里带 `parentChunkId`——有它说明被二次拆分过，属于"最差情况"的样本。数据跑单元测试就能拿，不用上线验证（参考 LangChain4j 的 `MarkdownHeaderParentTextSplitterTest`）。

我的实例文档拆成 1894 段，chunkSize=1000 时只有 90 个左右被二次切分的父分段，刚好满足 95% 召回率下限，所以定了 1000。

## A/B 收敛

初始值定好后，准备 50–100 个真实用户问题，标注正确答案所在片段，对比参数组合：比如 chunkSize ∈ {256, 512, 768} × overlap ∈ {10%, 20%}，看检索准确率。

重点分析召回失败的 query，失败原因通常就两类：相关片段被切碎了，或者块太大把关键信息稀释了。前者调大 overlap 或缩小 chunkSize，后者反过来。

## 小结

参数本身不是重点，流程才是：通用起点 → 文档类型修正 → parentChunkId 统计量化召回下限 → 真实 query A/B 收敛。整个过程在单元测试里闭环，不需要上线试错。
